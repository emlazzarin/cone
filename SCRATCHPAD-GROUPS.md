## Phase 3c-lite shipping notes (2026-07-01)

- **Rendezvous v2 in one shot with links**: rooms addressed by `SHA-256(secret)` (domain-separated from key derivation), cleartext per-offer `role` (`pair`/`descriptor`/`join`) driving capacity, per-role TTL ceilings, and visibility (joiners see descriptor + self only), `DELETE` = revocation. Clean break: `/v2/exchange`, no v1 path kept. Room transition logic is a pure exported `applyExchange` so the worker is unit-tested without DO plumbing.
- **A join may arrive before its descriptor** (kept from the sync-code race — Promise.all in tests/live); it waits in the room. Consequence: a mistyped token doesn't 404, it times out like a wrong code.
- **Stable descriptor nonce** (`GroupInviteLink.nonce`): servicing re-posts the descriptor each pass; without a stable nonce → new participantId → "room already has a descriptor" 409 on the second sync.
- **Token case-sensitivity**: `cone_gi_v1_` tokens are base64url — `normalizeHandshakeCode` would corrupt them. `normalizeRendezvousSecret`/`inviteScopedKey` branch on the prefix; codes stay case-insensitive. Test pins this.
- **Failed adds are marked serviced but don't consume a use** — one unreachable joiner can't wedge or exhaust a link.
- Live five-actor run passes: Bob mints `--link`, Erin pastes the token, Bob's `inbox sync` admits her, welcome auto-allows, exhausted link retires.

## Phase 3b shipping notes (2026-07-01)

- **Payload type discrimination is in the ciphertext, not the schema label**: `decryptJson` doesn't authenticate `schema`, and pairing offers carry no `type` field — a group descriptor decrypted in a pairing flow would have passed pairing's old `inboxId !== mine && env` check (descriptor has no `inboxId` → `undefined !== mine` is true). Both invite payloads carry explicit `type` fields, the invite finders require them, and `decryptPeerOffer` now skips any typed payload. Same code space, no cross-flow reads.
- **Pending-join rule runs before the blocked-adder rule** in `applyGroupAddPolicy`: entering a code seconds ago is stronger, fresher intent than a stale deny. It also doesn't require `addedByInboxId` (the pending match is on conversation id alone).
- **Pending joins live in `ConeStoreMetadata.pendingGroupJoins`** — the Phase 1 metadata-key-whitelist bug class again: BunSQLiteStore's `getMetadata` needed the new key added explicitly (`parseJsonArray`); MemoryStore/IndexedDB spread through for free.
- **Pending TTL is 24h, not the code's 10 minutes**: the inviter adds within seconds, but the joiner's *next sync* (which delivers the welcome) may be much later; an expired entry just falls back to the Request path, so long is safe.
- **CLI `group invite` takes `--code`** so scripts (the live test) can mint the code out-of-band à la `cone pair` and hand it to both actors; interactive use mints internally and prints it before polling (two JSON documents in JSON mode).
- **TUI render change**: a `pending` form used to hide `resultLines`; the invite form needs the code on screen *while* waiting (it's what gets read aloud), so pending now renders resultLines above kind-specific waiting copy.
- Rename fallout fixed in the same push: the shorter "Cone" TUI header freed enough width that a raw inbox-id title reached the top bar unshortened at width 100; the header context now goes through `convTitle` like the list rows.
- 156 unit tests pass; the live script gained a fourth actor (Dave) joining via code — not yet run against the dev network this session.

## Phase 1 shipping notes (2026-06-12)

- **Scope deltas vs the plan above:** adapter-level admin ops (add/removeAdmin, add/removeSuperAdmin) and updateName/Description were deferred to Phase 2 — thin passthroughs with no Phase 1 consumer weren't worth three fakes of churn. Surfaces got slightly *more* than "CLI minimal": groups render in TUI/PWA chat lists and transcripts, group sends route via `sendToConversation`, accept/block are conversation-scoped, read receipts are kind-gated. The GroupUpdated → cone.group.update.v1 envelope skips the admin-change arrays for now (add when Phase 2 renders them).
- **Streams:** one `streamAllMessages` per conversation type (`Dm` + `Group`), injected as `dmConversationType`/`groupConversationType`; every `IncomingMessage` carries `conversationKind`. `Dm` vs `Group` narrowing for `getConversationById` uses an `addMembers`-presence duck check (`isSdkGroup`).
- **Denied-inbox set** lives in `ConeStoreMetadata.deniedInboxIds`, maintained by Cone-side consent writes; backs the in-group sender drop (stream + views). Denials made on other devices reconcile via `adapter.getConsent` in the add policy; a consent-stream subscription can tighten this later.
- **Live test caught two real store bugs** (worth remembering as a class): BunSQLiteStore's `peer_inbox_id` column was NOT NULL (group rows have no peer → rebuild-table migration `relaxPeerInboxConstraint`), and `getMetadata` whitelisted only the two timestamp keys while `putMetadata` `String()`-ed values — `deniedInboxIds` would have been silently dropped/corrupted. JSON `data` columns made the *model* migration-free, but the denormalized columns and metadata key whitelist still bite.
- Live run validated on dev network: welcome → `unknown` + `addedByInboxId` populated (stranger-adder → Request; contact-adder → auto-allow), group fan-out over live streams tagged `group`, creator = superAdmin in `members()`. One Bun teardown segfault observed on a `cone send` exit (nightly bindings flake, command had succeeded; passed on re-run) — watch for recurrence.

## Design decisions

- **Toggle gates on address-book contacts** (named entries), not all allowed peers — Eddy 2026-06-12. Someone accepted-but-unnamed still lands in Requests when they add you.
- **No auto-contacts from any invite flow** (including the synchronous code — a deliberate divergence from pairing's mutual save). Instead, proposed-name/profile *suggestions* ride invite payloads and the UI offers one-tap save. Generalizes into the self-profile/share-card track (see Open items).
- **Knock servicing is group-wide, not creator-only**: the invite secret is shared into the group as a control message; any member with the token whose role passes the add policy can admit. No privilege escalation — under the default policy members can mint invites anyway; in `--locked` groups only admins' adds succeed.
- **Leave ≠ block**, both offered: leave (`requestRemoval`) is visible to the group (`leftInboxes`); block (deny GroupId) hides locally while silently remaining a member.
- **Creation presets**: default (`All_Members`) or `--locked` (`AdminOnly`). Custom `PermissionPolicySet` deferred.
- **Group name is shared network state** (any member can edit under default policy) — unlike Cone's local aliases. A local title override is deferred.
- **One key per agent**: every device/process on a SECRET KEY is an XMTP installation (max 10/inbox); agent fleets need distinct keys. Document this.
- **MLS history honesty**: new members can't see pre-join messages (forward secrecy). State it in UI copy; it is not a bug.

## Verified facts (researched 2026-06-11/12; SDKs: node 6.1.0-nightly, browser 7.0.0)

- **No native invite-link primitive.** Membership changes only when a member client with add permission calls `addMembers`. Convos (Ephemera) does links via a backend + an accepting agent — same shape we get from rendezvous v2 + `cone listen`.
- **Group consent**: `ConsentEntityType.GroupId = 0`, entity = conversation id. A group you create is auto-`Allowed` (libxmtp sets it on the create path); a group you're added to is `Unknown` — **no SDK auto-allow rule exists**; `conversation.addedByInboxId` is the documented app-layer hook.
- **Default permission policy** (libxmtp `default_policy()` + docs): add member = all members; remove member = admin; metadata = all members *except* disappearing settings = admin (min protocol version = super admin); add/remove admin + permission changes = super admin. Creator = sole super admin; **super admin cannot leave**; `addSuperAdmin` is additive (multiple super admins legal).
- **`GroupUpdated` content**: `{ initiatedByInboxId, addedInboxes, removedInboxes, leftInboxes, metadataFieldChanges{fieldName,oldValue,newValue}, addedAdminInboxes, removedAdminInboxes, addedSuperAdminInboxes, removedSuperAdminInboxes }`; `isGroupUpdated` guard exported by both SDKs.
- **Streaming**: `streamAllMessages` spans conversation types and accepts `conversationType` + `consentStates` filters; `streamAllGroupMessages`/`streamAllDmMessages` variants exist. `listGroups`/`listDms` split; distinguish via `instanceof Group/Dm` or `metadata().conversationType` (Dm=0, Group=1).
- **`createGroupOptimistic`** creates offline/instant, publishes on first send. `CreateGroupOptions`: `{ permissions, groupName, groupImageUrlSquare, groupDescription, customPermissionPolicySet, messageDisappearingSettings, appData (≤8KB, policy-gated) }`.
- **`members()`** → `GroupMember { inboxId, installationIds, permissionLevel (Member=0/Admin=1/SuperAdmin=2), consentState, accountIdentifiers }`.
- **Limits**: 250 members/group; 10 installations/inbox; ~1MB message cap; no pre-join history (welcome carries current-epoch secrets only).
- **Disappearing settings are identical on groups** (methods live on the base conversation) — retention work generalizes nearly free; timer changes admin-gated by default.
- **Rendezvous v1 weakness**: the worker receives the raw code (`idFromName(body.code)`) while offers are encrypted under `codeScopedKey(code)` — an honest-but-curious worker could decrypt offers. v2's hashed room ids fix this for links and pairing alike.
- Browser/node splits follow the known pattern (MaybePromise): group getters are sync on node, cached-or-async on browser; `syncAll` returns a summary (node) vs void (browser); `countMessages` number vs bigint.

## Deferred from 3c (revisit with Phase 4 / after PWA hosting)

Decided with Eddy 2026-07-01. Constraint recorded then: **agents are optional group members — they can be added, but no administrative feature may require one to be present or online.** Any revisit must design the human-only degraded mode first.

- **Knock-by-default links**: join requests queue in the room and surface Requests-style to members who can admit. Deferred because it's most of 3c's complexity (queue in the room, admit UX on three surfaces) and its servicing story is weak without an always-on member: a knock stalls until someone with the secret has the app open. An agent concierge makes knocks instant, but per the constraint above an agent cannot be the design's load-bearing piece — the human-only path (slow admits) must be acceptable on its own before we build this. `--auto` capability links (what 3c-lite ships) remain the escape hatch.
- **In-group invite-secret distribution (`cone.group.invite.v1`)**: sharing the token into the group so any authorized member can service joins. Two unresolved wrinkles: (1) MLS forward secrecy — members who join *after* the mint can never see the control message, so "any member" is really "any member since mint" unless the secret is re-sent on membership changes (creeping complexity); (2) every holder polling rendezvous for every live link is background work and tells the worker which clients watch which rooms. Revisit only if minter-serviced links prove too unreliable in practice.
- **Joiner-to-joiner privacy in link rooms**: v2 posts carry a cleartext `role` (descriptor vs join) so the worker can return join offers only to the descriptor holder; if that ever changes, joiners could decrypt each other's identities under the shared token key. Note kept here so the constraint isn't lost.
