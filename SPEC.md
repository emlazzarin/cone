# Cone Product Spec

Cone is a Bun-first TypeScript product with three surfaces: a static installable PWA (ConePWA), a terminal chat UI (ConeTUI, `cone chat`), and a CLI/library for agents and developers (ConeCLI) — ConeTUI and ConeCLI ship in the one `cone` binary. Users see the product name "Cone" everywhere; ConePWA, ConeTUI, and ConeCLI name the surfaces in docs and code. All three unlock the same XMTP account from a long `SECRET KEY`, can message any XMTP-reachable identity, save local address-book entries, and pair with an ephemeral handshake code. Where this spec says "both surfaces" it means the two rendering surfaces, ConePWA and ConeTUI.

Pre-release policy: *local state* carries no upgrade paths — schema changes regenerate it. The *protocol* is different: everything in "Protocol Compatibility" below is frozen now, because those are the surfaces that, once two users have connected, can never change without stranding them.

## Protocol Compatibility

The social graph lives in XMTP-native state (DM threads, MLS group membership, consent records) keyed by inbox IDs; Cone must never orphan it. These invariants are **frozen** and guarded by golden vectors in `packages/core/tests/vectors.test.ts` — a change that trips those tests is reverted, or shipped as a *new* version label alongside the old, never as an edit:

- **Identity derivation.** The HKDF salt `cone/v1/<env>/<accountId>`, the labels `xmtp-wallet` / `xmtp-db` / `cone-storage` / `backup-archive`, and the `cone_sk_v1_` secret format (version byte + 4-byte checksum). The wallet key determines the address and therefore the XMTP inbox — the account *is* this derivation. The env is part of the salt, so one SECRET KEY is a different identity per network; production is the shipping default everywhere, and a graph formed on one env can never move to another.
- **Rendezvous key material.** `cone-pairing-code:v1` / `cone-invite-token:v1` key derivations, `cone-rendezvous-room:v1` room addressing, handshake-code normalization (lowercase, whitespace→dash), and the case-sensitive `cone_gi_v1_` token format. Two different builds must land in the same room with the same keys forever.
- **The envelope content type identity.** Authority `cone`, type `envelope`, major version 1 (see Messaging). Minor bumps must stay readable by every 1.x client; a payload a 1.x client cannot read is a new major version, which old clients render via its fallback text.
- **Payload discriminators.** Every payload in the rendezvous keyspace and every wire envelope carries a self-describing `type` (`cone.pairing.offer.v1`, `cone.group.invite.descriptor.v1`, `cone.group.invite.join.v1`, `cone.*` envelopes). The cleartext `schema` label on encrypted offers is what lets an old client tell "newer version" from "nothing there yet".

Evolution rules for everything above the frozen layer:

- **Envelope fields are additive.** New fields on an existing `cone.*.v1` type must be optional and old fields are never repurposed (the tolerant-reader contract; `GroupUpdateEnvelope`'s optional admin arrays are the pattern). A change old readers cannot ignore is a new `.v2` type.
- **Unknown `cone.*` control types are hidden by contract.** Old clients suppress any `cone.*` envelope they don't recognize, so a new control type degrades to silence — which means anything *user-visible* must ship as app JSON (old clients render `value.text`) or as a new content type with a fallback, never as a bare new control type.
- **Rendezvous roles are server-first.** The worker validates the role enum strictly, so a new role deploys to the worker before any client sends it. The `/v2/exchange` contract for existing roles never changes; a breaking transport change is `/v3` alongside `/v2`.
- **Capability negotiation** rides the pairing offer's `capabilities` array (v1 sends `['text', 'json']`); readers ignore unknown entries.
- The XMTP SDKs are pinned exactly; upgrades stay within XMTP's supported libxmtp window (libxmtp, not Cone, owns MLS group-state compatibility).

## Architecture

- `packages/core`: shared product model, secret parsing, deterministic key derivation, contact/address-book logic, backup encryption, pairing encryption, storage interfaces, the adapter-facing `ConeClient`, and the SDK-agnostic XMTP adapter implementation (`@cone/core/xmtp`) that both adapter packages reuse.
- `packages/cli`: `cone` binary, Bun SQLite persistence, command parsing.
- `packages/xmtp-node`: XMTP Node SDK wiring (client creation, signer) for CLI and agent use.
- `packages/xmtp-browser`: XMTP Browser SDK wiring and encrypted IndexedDB store for the PWA.
- `apps/web`: ConePWA — Vite + Preact PWA.
- `apps/rendezvous`: Cloudflare Worker/Durable Object rendezvous service.

## Secret Model

`SECRET KEY` format is `cone_sk_v1_<base64url-payload>`. It contains a 32-byte random seed, a version byte, and checksum metadata. The seed derives labeled keys for XMTP wallet signing, XMTP local DB encryption, Cone storage encryption, and backup archives. Pairing-offer encryption is keyed by the normalized handshake code alone — the peer cannot know any account-derived secret before pairing completes.

## Messaging

Cone resolves identities through the configured XMTP adapter. v1 supports inbox IDs and EVM addresses. Address-book names are local aliases that resolve to canonical inbox IDs. Before sending, Cone asks the adapter whether the resolved identity is messageable.

**Content types are provenance.** User text rides XMTP's standard text content type and is always rendered verbatim — inbound text is never parsed for meaning, so a typed message can never impersonate a Cone envelope. Every Cone-specific payload (read receipts, pair confirmations, app JSON) rides the custom **Cone envelope content type** (`cone/envelope:1.0`), registered as a codec in both adapter packages: JSON with a self-describing `cone.*` `type`. Control envelopes declare no fallback, so to a non-Cone XMTP client they are invisible rather than JSON noise; app JSON declares a human-readable fallback (its `value.text` or a shape summary). Inbound envelopes are accepted only from that content type, and `cone.group.update.v1` is rejected there outright — group updates are minted exclusively by decoding XMTP's own `GroupUpdated` system messages, so a forged "Alice added Bob" system line cannot be sent as a message. Content in a type this build cannot decode renders its self-describing `fallback` when the sender declared one and stays hidden when they did not — a newer client's messages degrade the way that client intended instead of vanishing.

`client.sync()` is the explicit account-level network refresh. It asks the XMTP adapter to sync conversations/messages, persists conversations and encrypted message snapshots into Cone storage, and records sync metadata. `client.listConversations()` and `client.listMessages()` are local read-model calls.

**One peer is always one thread.** XMTP can hold several MLS DMs for a single peer pair (both sides initiated a conversation); the SDK stitches them, and Cone's adapter lists only the canonical DM (`includeDuplicateDms: false`). Duplicate rows that reached local storage anyway — persisted by an older build, or created mid-session by a message streamed in a duplicate — are folded into the canonical thread on every sync: their history moves, the row is deleted. Self-DMs are hidden from chat lists and no "Me" contact is auto-created — Cone has no notes-to-self surface yet, and XMTP models self-messaging awkwardly.

## CLI Account And State

The CLI has no local selector. The cryptographic account is determined by the `SECRET KEY`, with the default derived account label currently fixed to `main`. `XMTP_ENV` selects the network and defaults to `production`; `dev`/`local` are explicit opt-ins for testing (env-scoped derivation keeps their identities separate from the production account).

By default, the CLI uses one remembered secret and one local state database. `CONE_HOME` is the single path override — one directory holding config and state — for tests and concurrent agent runs (the exact-path `CONE_STATE_PATH`/`CONE_CONFIG_PATH` knobs were removed: their precedence over `CONE_HOME` let a repo `.env` silently share one state database across actors). `cone config` prints the effective configuration and the source of every value (code default, config file, or environment) without unlocking an account.

CLI output is JSON by default for agent use. `--plain` switches supported commands to human-readable output. In JSON mode, every failure is one structured object on stderr — `{"error":{"code","message"}}` with stable machine-readable codes — because agents parse errors and free text forces them to guess.

**The agent read model is poll-shaped as well as stream-shaped.** `cone listen` serves daemons; `cone messages [--cursor-name] [--peek]` and `cone wait [--timeout-ms]` serve turn-based agents that wake → check → sleep: sync first (a failed sync is `SYNC_FAILED`, exit 1 — never "nothing new"), then return inbound messages from allowed conversations since a durable named cursor (control envelopes never wake an agent, on any of the three commands). Exit codes are part of the contract everywhere: 0 = new messages, **3 = nothing new** (including `listen --once` timeouts), 1 = error. `client.pollMessages` backs both; cursors are opaque positions over the store-stamped ingestion sequence (`StoredMessage.seq` — SQLite rowid, memory counter), so ordering never trusts sender-supplied `sentAt` and a late-synced older message can never be skipped; `wait` re-syncs once after subscribing so nothing falls into the drain→subscribe gap. Reads present the sender's payload, not transport plumbing: app-JSON envelopes are unwrapped at view time (`json` = the payload, `replyTo` and `conversationKind` first-class); control envelopes stay wrapped because their type is their meaning. Structured payloads ride `cone send --data '<json>'` with `--reply-to` correlation; `--idempotency-key` is honest **at-most-once**: the key is claimed (scoped to the resolved recipient) before publishing and settled after — a retry gets the original result (`deduplicated: true`), a cross-recipient reuse gets `IDEMPOTENCY_CONFLICT`, and a crash mid-send gets `IDEMPOTENCY_IN_FLIGHT` rather than a guess. JSON output is NDJSON (one compact document per line). `cone doctor` runs the health checks (secret, state DB, rendezvous via `HttpRendezvousClient.probe`, XMTP) as `{name, ok, detail}` JSON. The CLI state DB runs in WAL mode so concurrent `listen` + `send` processes against one `CONE_HOME` are safe.

`cone inbox sync`, `cone inbox`, and `cone inbox read <conversationId|contactName|inboxId>` provide non-TUI validation surfaces for the local inbox read model; `cone inbox` lists `allowed` conversations only and notes any pending request count. `cone requests` is the explicit Requests surface: `cone requests [list]` lists unknown senders (`--denied` lists blocked ones), `cone requests accept <target> [--save-as <name>]` allows a sender (optionally saving a named contact), and `cone requests block <target>` denies the peer inbox. `cone listen` streams `allowed` senders only — the agent boundary. `cone chat` opens a lightweight terminal UI with four primary modes: `Chat(select)`, `Chat(talk)`, `Contacts(select)`, and `Contacts(edit)`. The chat list is sorted by most recent activity and shows last-message previews, relative times, and unread counts (shared formatting with the PWA via `@cone/core`). `Chat(select)` exposes `n` for a structured new-message form with contact/conversation suggestions, `r` to name the selected chat's peer (saves/renames a contact), `c`/`p` to create or join a pairing code (parity with the PWA Pair tab), `/` for a live chat filter, and `t` to toggle the Requests sub-surface (where `a` accepts and `b` blocks, blocking confirmed by a second press). Contacts also expose pairing: `c` creates a code and `p` joins a code. Active form fields show a cursor.

ConeTUI renders as titled rounded panels in the PWA's CRT language (one amber accent, dim metadata): a header with the brand and highlighted section tabs, list/thread panes, a boxed composer, and a footer whose leading chip names the current mode (CHATS/REQUESTS/FILTER/TALK/COMPOSE/CONTACTS/EDIT/GROUP) — the active tab, the focused pane's amber border, and amber selection bars keep the current state visible at a glance. Layout resizes aggressively: two panes at ≥ 84 columns, a single mode-appropriate pane below that (the PWA's mobile collapse), one-line chat rows plus a bottom-line composer on short terminals, and a minimal fallback under 44×9.

## PWA Interaction

The PWA is pointer- and touch-native with TUI-parity accelerators. It has no explicit select/talk modes; focus expresses the mode (typing in the composer vs. navigating). `1–5` switch sections (Chats, Contacts, Pair, Backup, Settings), `j/k` move the chat selection, `Enter` opens the selected chat (or starts a new message when none is selected), `n` composes a new message, `/` filters chats, `?` toggles a help overlay, `Esc` leaves typing. Conversation rows show avatar, last-message preview, relative time, and unread count; transcript lines share the CLI `HH:MM - sender: body` format. Read markers are stored locally per account. Within Chats, a Chats/Requests segmented toggle appears when there are pending requests (or the tab is open); the Requests sub-surface lists unknown senders with Accept/Block per row, and blocked senders are managed (unblock) from Settings. A Settings toggle hides the Requests tab entirely.

Both surfaces render outbound sends optimistically: the message is appended to the transcript and the composer clears before the network round-trip resolves. A delivered message is reconciled against the optimistic row (matched by body and a five-minute send-time window); a failed send is marked and offers retry or delete. Optimistic rows are local-only and never persisted.

## Delivery Status

XMTP exposes a sender-side delivery status (`DecodedMessage.deliveryStatus`: unpublished/published/failed) but no per-recipient delivery ack. The adapter sends synchronously — a resolved send is published; a rejection is a delivery failure surfaced to the optimistic UI. `SentMessage.deliveryStatus` carries the result. The adapter read paths (`listMessages`/`sync`/`streamMessages`) keep only published messages (`normalizeDeliveryStatus` handles the SDK's numeric enum and string forms), so a message that failed to publish cannot later sync in and appear delivered. Successful sends are silent; failures are the only visible state, with retry (resend) and delete (discard the optimistic row).

## Read Receipts

Read receipts are a Cone control message (`cone.read.v1`) riding the Cone envelope content type, like pairing confirmations. They carry no fallback, so a non-Cone client sees nothing (the correct rendering of a read receipt); they interoperate only between Cone clients and are hidden from the transcript. When a conversation is viewed with read receipts enabled, the client sends one receipt acknowledging the newest inbound message, deduped so repeated views don't re-send. `latestReadOutboundId` derives, from the peer's most recent receipt, the single most recent outbound message at or before it; both surfaces show one `✓✓ Read` marker there. The marker is rendered inline in a reserved right-hand gutter on outbound rows (not as its own line), so it moves between messages without reflowing the transcript and never crowds wrapping text. The setting defaults on, persists per surface (PWA: localStorage per account; CLI: `readReceipts` in config), and is symmetric: when off, the client neither sends receipts nor shows peer read state (no gutter is reserved), and only failed sends are marked.

## Disappearing Messages

Disappearing messages ride XMTP's native conversation-level settings (`MessageDisappearingSettings { fromNs, inNs }`), not a Cone control message — so timers interoperate with other compliant XMTP clients and either DM participant can change them. The adapter exposes `getRetention`/`setRetention` and converts at the ns↔ms boundary; Cone models the setting as `MessageRetention { durationMs, fromAt }` mirrored on `ConeConversation.retention` with the same lifecycle as the consent mirror: mirror-first writes (`client.setRetention(conversationId, durationMs | null)` updates local state immediately, the network settings write is best-effort), reconciled from the network on every sync.

Expiry is **derived, never stored**: a message sent at or after `fromAt` disappears `durationMs` after its send time, computed from the conversation's *current* retention. Enabling a timer is forward-looking (earlier history never expires), and changing or removing the timer immediately re-derives the whole conversation — matching XMTP semantics. `ConeMessage.expiresAt` is computed at read time for UI use.

libxmtp's cleanup worker only deletes from the XMTP-level local DB; Cone's own encrypted snapshots are enforced separately. `listMessages` filters expired messages at view time (so they are never rendered, even between purges), and `client.purgeExpiredMessages()` deletes them from Cone storage — it runs during `sync()`, before `exportBackup()` (a backup never contains expired messages), and before any settings change (a message that already hit its timer is gone for good and cannot be resurrected by relaxing the timer). Purged messages keep their processed-message markers so a copy still lingering in the XMTP DB cannot re-ingest on the next sync.

Both surfaces share the preset vocabulary (off, 30s, 5m, 1h, 8h, 1d, 1w, 4w — Cone convention; XMTP itself takes any duration). Custom durations are first-class: the TUI accepts free text (`45m`, `6d`) and every surface displays a non-preset value as-is (the PWA select grows an extra option for it) rather than snapping it to a bucket. Durations format/parse via `formatRetention`/`parseRetention` (s/m/h/d/w units). CLI: `cone timer <target> [<duration|off>]` shows or sets; `cone inbox read` JSON carries `retention` and `expiresAt`. TUI: `e` in `Chat(select)` opens a one-field picker (Up/Down cycle presets), the thread header shows a `timer 1h` chip (ASCII — the hourglass glyph is double-width in many terminals), and an exact-expiry refresh drops rows the moment they expire. PWA: a `⌛` select in the chat header — `e` focuses it, and while focused `j/k` or arrows step a draft value, Enter applies, Esc leaves (pointer selection applies directly); a `⌛` chip marks conversation rows with an active timer, and the 8-second poll drops expired rows. Timer changes are announced via the status line; the persistent indicator is the header chip. A change made by either side also arrives as a `GroupUpdated` metadata event (two field changes: `from_ns` + `in_ns`) and renders as a single attributed system line carrying the new duration — "Alice set disappearing messages to 1h" / "Alice turned disappearing messages off".

Because settings changes ride conversation metadata, not the message stream, every surface must sync to see a change made elsewhere: the TUI's 60-second auto-sync covers it, and the PWA syncs once at session start and every 60 seconds thereafter (its 8-second poll only re-reads local state).

Deletion is cooperative, not cryptographic: a peer on a client that does not honor the settings can retain anything. The setting is honest hygiene shared between compliant clients, and the UI copy says so.

## Consent

XMTP consent is Cone's anti-spam and trust boundary. Every conversation carries a consent state — `allowed`, `unknown`, or `denied` — mirrored locally on `ConeConversation.consentState` for fast, offline-capable UI and reconciled from the network on every sync. Consent is **peer-inbox-level**: blocking targets the inbox, so a denied sender cannot reappear with a fresh conversation.

The default is strict. Main chat surfaces show `allowed` only. Unknown inbound senders become **Requests** — a sub-surface of Chats on both apps (not a new top-level section) — and never an address-book entry; a contact is created only on accept. `denied` conversations are hidden from all normal lists, streams, and compose suggestions, and are managed from a blocked list (PWA Settings). Consent is implied by intent: a successful pairing, an outbound send, accepting a request, and manually adding a contact all mark the peer `allowed`. Accepting marks `allowed` (optionally saving a named contact in the same flow); blocking marks `denied`.

Writes are mirror-first: the local state updates immediately and the XMTP network consent write is best-effort, reconciled on the next sync. If the network write fails, the decision still holds locally (treated as local-only until it propagates). `client.sync()` pulls `allowed` + `unknown` (so Requests populate) and never `denied`. View-time filters (`isAllowedConversation` / `isRequestConversation` / `isDeniedConversation` in `@cone/core`) split the single read model; every conversation row carries a `consentState`.

**Agent boundary.** `client.streamMessages` defaults to `allowed`-only — an unknown sender can never drive an agent's workflow, tools, or response generation. Human surfaces opt in to `['allowed', 'unknown']` so Requests update live; `cone listen` and the example agent keep the strict default. Unknown senders are visible only through the explicit Requests surface (`cone requests`); accepting consent is the boundary before any agent behavior runs. Read receipts are gated on `allowed`, so previewing a Request never acknowledges it to the sender.

Consent maps 1:1 to the XMTP SDK `ConsentState` enum at the adapter boundary (`@cone/core/xmtp`), via `setConsent`, `getConsent`, and consent-filtered stream/sync/list calls. Inbox-level consent covers DM peers; group conversations carry their own consent keyed by conversation id (XMTP `ConsentEntityType.GroupId`) — see Groups.

## Groups

Conversations carry `kind: 'dm' | 'group'`, required on every row and on every streamed message. A group row mirrors the XMTP group's shared state: `groupName`/`groupDescription` (network metadata any member may edit under the default policy — unlike Cone's local contact aliases), `memberCount`, `addedByInboxId` (who added this account), and a cached member mirror `{ inboxId, level, consentState }` refreshed on sync for offline info panels. The adapter opens one message stream per conversation type so every delivered message is tagged with its kind — a group message can never be persisted as a DM-shaped conversation attributed to whoever spoke first. A group message streamed before any sync fetches the real group shape via `getGroupInfo` (placeholder row reconciled by the next sync if offline).

`createGroup` uses XMTP's default permission preset (any member adds members and edits metadata; admins remove members; the creator is the sole super admin) or `locked` (the `AdminOnly` preset). Members resolve through contacts/identities and are deduped (the creator is added by XMTP itself); **invites never auto-create contacts**. Sending into a group uses `sendToConversation` (DM rows route through the identity path so reachability and implied-consent semantics are unchanged). Membership, metadata, and admin changes arrive as XMTP `GroupUpdated` system messages, decoded into a `cone.group.update.v1` control envelope (initiator; added/removed/left inboxes; admin and owner grants/revocations; metadata field changes) and rendered in group transcripts as attributed system lines via `formatGroupUpdate` ("Alice added Bob", "Carol renamed the group to Crew") — they stay out of previews, unread counts, and the agent message stream like any control message. Group transcripts open with the honest MLS note (`groupHistoryNotice`): a joiner's view starts at their join, the creator's at creation — pre-join history is cryptographically invisible, not withheld. Groups cap at 250 members.

**Administration.** `renameGroup` and `setGroupDescription` are mirror-first like consent (local row immediately, network write best-effort, sync reconciles) — and shared: every member sees the change, which is why group names are not local aliases. `setGroupMemberLevel(conversationId, member, 'member' | 'admin' | 'superAdmin')` diffs the member's current role into XMTP's separate admin/super-admin list operations; promoting someone else to `superAdmin` ("owner" in UI copy) is the transfer-ownership move — the lists are additive, multiple owners are legal, and XMTP forbids the last owner leaving, so surfaces guard leave with "promote another owner first". Permission failures are real errors surfaced to the user (policy is enforced by every member's client, not by Cone's UI). A member leaves via `leaveGroup` (`requestRemoval`, visible to the group as `leftInboxes`); being removed or leaving flips the mirror's `active: false` — the row and history are kept, sends fail fast with "no longer a member", and surfaces tag the chat as left.

**Group consent.** Creating a group or sending into one implies group consent (mirror-first, like DMs). Being added by someone else arrives as `unknown` and is resolved by the group-add policy, applied idempotently at sync/welcome time:

- Added by a **blocked inbox** → silently denied: no Request row, no signal back. Cone does not auto-leave — leaving is visible to the group (`leftInboxes`), blocking must not be. This also closes the re-add loop: every new group is a fresh conversation id, so without it a blocked sender could generate Requests forever.
- Added by an **address-book contact** with the **"allow contacts to add you to groups"** toggle on (the default; CLI config `groupAutoAllow`) → auto-allowed, straight into Chats.
- Anyone else (or toggle off) → stays `unknown`, a **Request** alongside DM requests. Accept/block go through `setConversationConsent`, which targets the peer inbox for DMs and the group id for groups; `--save-as` contact saving is DM-only.

**The block list follows you into groups.** XMTP gates group delivery per conversation, not per sender, so an allowed group still delivers messages from inboxes this account has denied. Cone maintains the denied-inbox set in store metadata (updated by every Cone-side consent write) and drops those senders' group messages before the stream handler and out of `listMessages` — a denied sender can never reach an agent loop through a shared group. Accepting a group means trusting its membership policy for everyone else.

**Agents.** The agent boundary is unchanged and sharper: streams default to allowed-only, which for groups means *explicitly accepted groups only*. `cone listen` builds its client with `autoAllowGroupsFromContacts: false` — even a contact's group add waits for an explicit `cone requests accept` — with `--auto-accept-groups-from-contacts` as the opt-in; the example agent keeps the strict default. Listen output carries the group context an agent needs: every JSON line has `conversationKind`, plus `senderName` (local contact) and `groupName` when known, resolved best-effort from the local store. Mentions are a text convention, not a content type: `isAddressedTo(text, aliases)` in `@cone/core` matches `@alias` at token boundaries, and the reference agent replies in groups *only when addressed* — the guard that keeps multiple agents in one room from feeding each other reply loops. `examples/agent` is a group-capable concierge: strict consent, respond-when-addressed, and a periodic `sync()` that also services any invite links the agent minted (groups never *require* an online agent; running one just makes its own links admit instantly). Read receipts stay DM-only — in a group they would broadcast to every member — so previewing a group Request acknowledges nothing.

CLI: `cone group create --member <ref> [--member ...] [--name] [--description] [--locked]`, `cone group info|add|remove|rename|describe|promote|demote|send|leave <conversationId|name>` (`promote --super` transfers ownership); groups flow through `cone inbox`, `cone inbox read`, and `cone requests` with their `kind`. TUI: `i` on a group opens the **group info** mode — members with roles (contacts-first names, `[owner]`/`[admin]` tags, `[blocked]` badges), `a` add member, `r` rename, `+`/`-` promote/demote, `d` remove (two-press), `e` timer, `x` leave (two-press, visible), `b` block (two-press, silent). PWA: the `group · N members` header meta toggles an info panel with the same operations (rename input, per-member role/remove buttons, add-member input, Leave/Block with honest confirm copy). Both surfaces label inbound group messages by sender (contacts-first) and render `GroupUpdated` system lines inline. **Leave ≠ block** everywhere: leaving is visible to the group; blocking (deny the group id) hides it locally without telling anyone.

**Invite codes.** The synchronous group invite reuses the pairing machinery asymmetrically. The inviter — any member whose role passes the add policy — mints a handshake code and posts an encrypted *group descriptor* (`cone.group.invite.descriptor.v1`: group name, member count, inviter identity, conversation id) to the code's rendezvous room; the joiner posts a *join request* (`cone.group.invite.join.v1`: identity plus an optional proposed name). The inviter's client decrypts the request and calls `addMembers` directly — auto-add is correct because the code was created seconds ago, so intent is unambiguous. Codes are single use (the room caps at two participants) and expire after 10 minutes; payloads carry explicit in-ciphertext `type` fields so an invite payload can never be misread as a pairing offer under the same code space, and both sides reject cross-network payloads. **No contact is auto-saved on either side** — the joiner's proposed name rides the payload as a save suggestion. `addGroupMembers` gates every add (direct or invite) on `canMessage` reachability.

The joiner records the join as **pending** (store metadata, 24-hour window — the inviter adds within seconds, but the joiner's next sync may be later). Membership arrives as the normal XMTP welcome, and the group-add policy consumes a matching pending join *before* its other rules: the group is auto-allowed (requesting to join is implied consent) instead of landing in Requests, even though the inviter is a stranger. An expired or cancelled pending join falls through to the usual policy. CLI: `cone group invite <group> [--code <code>] [--timeout-ms]` (prints the code, waits, adds the joiner and suggests a `contacts add` for the proposed name), `cone group join <code> [--share-name <name>]`, `cone group joins [cancel <conversationId>]`. TUI: `v` in group info mints a code that stays on screen while the invite waits in the background (same non-blocking pattern as pairing); `g` in Chats joins by code. PWA: an "Invite by code" row in the group info panel (code + countdown while waiting) and a "Join a group" card on the Pair tab that syncs immediately after the request so the welcome lands fast.

**Invite links.** The async tier rides the same payloads with a capability token, `cone_gi_v1_<secret>` — base64url and case-sensitive, unlike spoken codes. Minting posts the group descriptor into the token's room with a long TTL (default 7 days); the token **is** admission (auto-admit, Discord-style), so links default to **one use**. Joining is the same `join` flow — the descriptor is already in the room, so nothing waits — and records the same pending join. **Only the minting client services its links**, during every `sync()`: it polls its rooms, decrypts new join requests, and calls the same reachability-gated add; a failed add is marked serviced without consuming a use, so one bad request can't wedge a link. Exhausted, revoked, or orphaned links (the group is gone or the minter left) tear their rooms down. Nothing is distributed into the group and no other member — in particular no agent — is assumed present or online; knock-style admission and shared servicing are deliberately deferred (SCRATCHPAD.md). CLI: `cone group invite <group> --link [--max-uses <n>] [--ttl <duration>]`, `cone group links [revoke <linkId>]`, and `cone group join <token>`; every join surface accepts a code or a token. TUI: `l` in group info; PWA: an "Invite link" row (copy/revoke) in the info panel. Clickable `https://<host>/#join=<token>` links wait on PWA hosting; until then tokens are pasted.

## Pairing

Handshake-code pairing is ephemeral and opt-in. Two participants enter the same high-entropy code. Each posts an encrypted offer (`cone.pairing.offer.v1`, an explicitly typed payload like everything in the rendezvous keyspace) to the rendezvous service. Once both offers exist, clients decrypt locally, confirm over XMTP, and save each other as contacts. The rendezvous service caps pairing rooms at two participants and expires offers after 10 minutes.

**Handshake failures are loud.** Every condition waiting cannot fix fails fast with a named cause instead of decaying into a timeout: the peer is this same account (two apps, one SECRET KEY), the peer is on a different XMTP network (both env names in the error), the peer's offer schema is from a newer Cone ("update and try again", detected via the cleartext schema label without decrypting), the code belongs to the other flow (pairing vs. group invite — the worker's role-mismatch rejection is relayed verbatim), or a `cone_gi_*` token that isn't valid v1 (truncated or from a newer Cone). Timeouts are reserved for the one case they mean: nobody showed up. Link servicing is the deliberate exception — it skips unreadable join requests rather than throwing, so one bad request can never wedge a link for everyone else.

Minting a code **immediately joins its room** on every surface — bare `cone pair`, `c` in the TUI, "Create code" in the PWA all print the code and start waiting in one step. "Create, then separately join your own code" is not a state that exists (it was a silent-timeout trap); `cone pair --print` remains for scripts that only need a code minted. Pairing the same account with itself fails fast with an explanatory error rather than timing out — two apps unlocked with the same `SECRET KEY` are one identity and already share their conversations.

The rendezvous protocol (v2) addresses rooms by `SHA-256(secret)`, so the worker only ever relays ciphertext it cannot decrypt — it never sees a handshake code or invite token (v1 sent the raw code, which is also the encryption key's input). Every offer declares a cleartext role — `pair`, `descriptor`, or `join` — letting the worker enforce capacity, per-role TTL ceilings, and visibility without decrypting: joiners under a shared invite see only the descriptor and themselves, never each other. `DELETE` on a room is revocation; addressing a room requires the secret, so any holder may revoke (a leaked token being revocable beats the reverse).

`cone pair <code> --share-name <name>` sends an optional peer-visible proposed contact name. `cone pair <code> --save-as <contactName>` saves the peer under a local contact name. Cone never sends local state selectors as identity hints.

## Persistence

The CLI uses `bun:sqlite`. Conversation rows (including the consent mirror), sync metadata, processed message IDs, contacts, and encrypted message payloads are persisted locally. The PWA uses IndexedDB and stores the full Cone snapshot encrypted with the derived storage key. Browser XMTP storage is treated as separate because XMTP does not use `dbEncryptionKey` for browser DB encryption.
